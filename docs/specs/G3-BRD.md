## 1. Business Problem

Prior to G3, `build_graph` assigned communities by source file: every symbol in `users/hdr.py` got community N, every symbol in `auth/handlers.py` got community M. This produces balanced clusters but ignores the actual dependency structure. If `auth/handlers.py` imports `users/hdr.py` 15 times, they should likely share a community — but the old code put them in separate ones.

L1 summaries (single-community chunks for context) and L2 "relevant areas" (community-scoped retrieval) both read this community partition. Wrong communities = incoherent summaries + wrong retrieval scope.

G3 replaces balanced-per-file with Louvain modularity over structural edges. Communities now match architectural boundaries instead of file boundaries.

## 4. Non-Goals

- Leiden algorithm (out of scope for G3; future optional upgrade via lazy-import)
- Multilevel Phase 2 (single collapse is sufficient for v1 dense code graphs)
- Community quality metric Q returned (v1 ships partition only)
- python-louvain / python-igraph as hard deps (stdlib-only philosophy)
- Overlapping communities (Louvain produces hard partition)

## 5. Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Louvain collapses real architecture to 1 community on tiny projects | Low | Medium | `_assign_communities` falls back to per-file grouping when `len(unique_comms) <= 1` |
| Carry-over community ID drift across incremental builds | Low | Medium | Key carry-over on `source_file + community` pair; re-read `_assign_communities` if drift observed |
| Resolution param ignored in practice (not tested against real graphs) | Medium | Low | γ=1.0 is default and safe; future tuning can add γ≠1.0 to CLI |
| Non-determinism from Python hash randomization | None | High | Verified: no `hash()` in path; sorted node iteration; `defaultdict(float)` is insertion-order stable |
