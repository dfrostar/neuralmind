## 1. Executive Summary

NeuralMind already ships three independent retrieval signals: dense vector similarity (ChromaDB), sparse keyword search (BM25), and learned graph-traversal (synapse spreading activation). Each signal runs in its own code path and produces a ranked list. But the system today picks **one** signal as the primary path (currently dense vector search with BM25 as a hybrid supplement via `_rrf_merge`) — it does not fuse all three into a single consensus ranking.

**The result:** recall is left on the table. Code entities that a dense embedding misses (e.g., an exact-function-name match that BM25 catches) are ranked below a distant semantic hit unless the hybrid merge catches it. Synapse co-activation — learned directly from how the agent actually navigates the codebase — has no direct influence on the candidate pool used for L3 deep search; it only *re-ranks* an already-selected set and swaps in at most 2 neighbors.

Reciprocal Rank Fusion (RRF) is a well-established meta-ranking technique that merges multiple ranked lists by scoring each result as `1 / (rank + k)` and summing across strategies. It is parameter-oblivious (no score calibration — just rankings), computationally trivial (O(N) on list merge), and has been demonstrated to produce 5–15% recall lifts over any single strategy in multi-vector retrieval benchmarks (Cormack et al., SIGIR 2009; commercial systems: Elasticsearch, Vespa, Cohere RRF).

This feature introduces a dedicated `rerank_fusion.py` module as the canonical home for the RRF algorithm, extends the current two-list merge to accept three signals (dense, sparse, synapse), wires it into the `ContextSelector` L3 pipeline as an **optional toggle** (default off for backward compatibility), and supplies test fixtures that verify ranking quality across all three strategies.

## 2. Business Problem

### 2.1 Siloed Retrieval Signals Leave Recall on the Table

**Problem statement:** NeuralMind's `context_selector.py` currently fuses dense (ChromaDB) and sparse (BM25) results via `_rrf_merge` (a hard-coded two-list merge on `ContextSelector`, line 252), but the third signal — synapse spreading activation — is **not fused at the candidate-ranking stage**. Instead:

1. **`_fetch_search`** (line 309) runs `embedder.search()` (dense) and `bm25_search()` (sparse) and merges them via `_rrf_merge`. This is the candidate pool.
2. **`get_l3_search`** (line 791) takes that fused pool, runs `_apply_structural_expansion` (precise code wiring), then `_apply_synapse_boost` (learned co-activation). The synapse boost **can** bring in new nodes via `get_nodes_by_ids` (line 699) — up to `_synapse_pull_in_max` items — but it does so as a **post-hoc swap** that displaces the weakest vector hits rather than participating in the initial candidate-ranking fusion.
3. **`bm25_search`** lives on `embedder.py` (line 628) and returns in the same format as `search()`.

**Concrete failure mode:** An agent frequently navigates `UserService.authenticate()` → `SessionStore.validate()` → `AuthMiddleware.handle()`. The synapse store has `validate()` highly co-activated with `handle()`. Yet if `handle()` ranks 18th in both vector and BM25 for a given query, it never makes the L3 top-4 cut. The synapse path can swap in at most `_synapse_pull_in_max` items (default 2) — but because it operates as a post-hoc displacement rather than a fused signal, it cannot compete on equal footing with dense and sparse retrieval during the initial ranking.

**Impact:** The learned graph — NeuralMind's crown-jewel differentiator — is treated as a post-hoc nudge rather than a first-class retrieval signal. Published benchmarks (Cormack et al., 2009; Baeza-Yates et al., 2020) show that multi-signal RRF consistently outperforms single-signal baselines by 5–15% in recall@k, a gap that directly translates to context quality for the agent.

### 2.2 The Current Hybrid Merge Is a Two-List Implementation

The existing `_rrf_merge` is:

- **Hard-coded to 2 lists:** signature is `(vec_results, kw_results)` — cannot accept the synapse third signal.
- **Embedded in ContextSelector:** It lives as a private method of the selector, not a reusable module.
- **No config surface:** `RRF_K = 60` is a class constant. It cannot be tuned per-project or toggled at runtime.
- **No dedicated tests:** The method is exercised only through integration paths. There are no unit tests for RRF ranking quality, tie-breaking, or degenerate inputs.

### 2.3 Why Now

v2.0 is expected to land all eight compliance/product gaps. v2.1 is the first opportunity for **pure retrieval quality improvements** that don't depend on the compliance use case. This feature:

- Has zero schema changes, zero new dependencies
- Requires minimal code (a single new module + three integration points)
- Delivers a 5–15% recall improvement measurable via the existing benchmark harness
- Is safely toggleable (default off, opt-in via env var)

## 4. Non-Goals

- **Weighted RRF variants** (e.g., per-strategy k, per-strategy weight boost) — deferred until the baseline three-signal RRF proves its value
- **Online learning of RRF weights** — cross-entropy minimization of RRF weights against human-annotated rankings is v2.2+
- **Replacing the existing `_rrf_merge`** — the old method remains for backward compatibility during the transition; a `@deprecated` warning will be added
- **Retrospective fusion for synapse already-run queries** — the feature applies to *new* queries only
- **Query-time rank cut adaptation** — n is fixed per query path as today

## 5. Use Cases

### UC-1: Agent Queries with All Three Signals Fused

**Actor:** LLM coding agent (via MCP or Claude Code hooks).

**Flow:**
1. Agent fires a query (e.g., "How does session validation work?").
2. `ContextSelector._fetch_search()` runs all three retrievals in sequence:
   - `embedder.search()` → dense ranked list (ChromaDB, cosine distance)
   - `embedder.bm25_search()` → sparse ranked list (BM25 term matching)
   - `synapse_recall()` (from spread activation) → graph-ranked list (Hebbian co-activation energy)
3. All three lists are fed into `rerank_fusion.rrf_merge()` with configurable `k`.
4. The fused top-k is returned for L3 rendering (max 10 candidates → budget-neutral).

**Result:** The agent gets a candidate pool that includes entities strong in *any* signal — not just the one that happens to dominate vector similarity.

### UC-2: Performance Regression Detection

**Actor:** Developer running `neuralmind benchmark`.

**Flow:**
1. Benchmark runs twice: once with `NEURALMIND_RRF=0` (baseline), once with `NEURALMIND_RRF=1`.
2. Reports `recall@k`, `precision@k`, and `mrr` for both configurations.
3. Regression gate on benchmark output: if RRF-on recall drops below RRF-off recall, flag the run.

**Result:** Continuous verification that the fusion layer doesn't regress.

### UC-3: Project-Specific RRF Tuning

**Actor:** Power user or self-improvement tuner (`PopulationTuner`).

**Flow:**
1. User sets `NEURALMIND_RRF_K=45` (more aggressive top-weighting) for a codebase with very sparse entity names.
2. The tuner cross-validates k as a tunable parameter candidate.
3. Results are persisted to the tuning registry and used on subsequent builds.

**Result:** Per-project calibration of the RRF constant, analogous to other tunable ContextSelector params.

## 6. Configuration Surface

| Config | Type | Default | Description |
|--------|------|---------|-------------|
| `NEURALMIND_RRF` | bool | `0` (off) | Master toggle. When off, existing `_rrf_merge` behaviour is preserved exactly. When on, the new three-signal RRF module is used. |
| `NEURALMIND_RRF_K` | int | `60` | RRF constant in `score = 1/(rank + k)`. Standard value from Cormack et al. Lower values weight top positions more aggressively. Must be ≥ 1. |
| `NEURALMIND_RRF_MAX_N` | int | `30` | Candidate pool size per input list. Controls how deep into each signal's ranking we fuse. Higher values capture more long-tail but increase merge time. |

## 9. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| RRF degrades precision (too much noise from long-tail signals) | Low | Medium | `NEURALMIND_RRF_MAX_N` caps per-list depth. Default 30. |
| Synapse signal is empty on cold-start graphs | Medium | Low | RRF gracefully handles empty lists (returns the remaining lists as-is). |
| Three embedder round trips (dense + BM25 + synapse) triple latency | Low | Low | BM25 is O(1) index lookup. Synapse recall is seeded from top-3 results (already fetched). Dense search is the only heavy query. |
| Existing `_rrf_merge` callers break during migration | Low | High | Keep old method as deprecated wrapper; new callers use `rerank_fusion.rrf_merge`. Default off. |
| Benchmark regression gate fails on noisy data | Medium | Low | Use bootstrap confidence intervals (already standard in benchmark harness). |
